# 万级设备容量说明

这份说明区分“管理上万台设备”和“同时播放上万路视频”。两者不是同一量级的问题，不能用一台
MediaMTX 或一张网卡承接全部流量。

## 当前已经完成的适配

- 床位、毯子、摄像头、设备绑定都支持搜索、筛选和分页。
- 病区地图首屏只展示有限病房，更多病房按需展开。
- 摄像头列表不会在后台为每一路建立连接，只有打开床位详情后才播放当前一路。
- 床位详情只在页面可见时刷新传感器快照，页面隐藏后停止无意义轮询。
- 传感器状态按批次写入磁盘，不会为每条 MQTT 消息同步重写整个状态文件。
- 告警使用独立持久会话监听，断线重连后可继续接收 Broker 排队的告警。
- 告警 WebSocket 重连后会自动拉取服务端快照，补回断线期间遗漏的状态。

这些改动能让页面在设备数量增加时保持可操作，但不代表当前单机已经通过一万路并发播放压测。

## 容量边界

视频容量主要由摄像头码率、观看并发、转码方式和出口带宽决定。

| 场景 | 估算方式 | 需要关注 |
| --- | --- | --- |
| 1,000 路 2 Mbps 接入 | 约 2 Gbps 入站 | 独立采集网卡、MediaMTX 分片 |
| 10,000 路 2 Mbps 接入 | 约 20 Gbps 入站 | 多台流媒体节点、交换机与存储网络 |
| 10,000 路 4 Mbps 接入 | 约 40 Gbps 入站 | 分片、专用网络、无中转转码 |
| 100 名护士各看 1 路 2 Mbps | 约 200 Mbps 出站 | 限制单用户并发观看 |

如果还要录像，需要单独计算写入带宽和保留容量：

```text
每天容量(GB) = 摄像头数量 × 单路 Mbps × 86400 ÷ 8 ÷ 1000
```

例如 10,000 路、每路 2 Mbps、保留 7 天，需要约 1,512,000 GB，也就是约 1.5 PB 原始存储。
生产环境应根据事件录像、低频抽帧或对象存储分层策略降低容量。

## 推荐部署拓扑

```text
摄像头 / 毯子设备
        |
        +-- EMQX 5 集群（至少 3 节点，固定域名）
        |
        +-- MediaMTX 分片组 A/B/C（每台只承载指定流）
                         |
Nginx / API Gateway -- Spring Boot 无状态实例
                         |
                MySQL（业务数据）+ Redis（最新状态）
```

### MQTT

- 使用 EMQX 5 的多节点集群和统一接入域名。
- 数据主题使用独立短连接或普通订阅；告警使用持久会话和独立客户端。
- 为离线数据队列设置明确上限，避免 Broker 因离线客户端无限堆积。
- 多 Spring 实例应通过共享订阅分摊消费，例如 `$share/blanket/data/...`，避免每台实例重复处理。
- 不要把每条原始数据永久保存到 JSON 文件；最新状态放 Redis，历史数据按业务需要进入时序库或分区表。

### 视频

- 每台 MediaMTX 承载固定数量的摄像头，控制面为摄像头分配流媒体节点。
- 摄像头播放地址必须来自后端下发的 `camera.playback`，不要在前端写死单一 IP。
- 可扩展时优先使用 HLS；WebRTC 用于少量关键床位的低延迟观看。
- 前端同一页面最多同时播放 9 路，普通用户建议 1–4 路。
- 禁止默认打开“全部摄像头自动播放”的总览墙。
- 流媒体节点按院区或楼层分区，避免单点故障影响全院。

### 后端与数据库

- Spring Boot 进程必须无状态，业务配置、设备关系、人员权限和告警进入 MySQL。
- 最新传感器值进入 Redis，并设置合理的过期时间。
- 原始高频数据不要直接写入关系库；按需抽样、批量写入时序存储。
- 所有客户端列表接口必须支持服务端分页，不能一次返回全部床位或摄像头。

## 上线前压测门槛

1. 先以真实单路码率跑 100、500、1,000 路接入。
2. 同时模拟 20、50、100 个浏览器观看，记录首帧时间、卡顿率和内存。
3. 将 MQTT 发布提高到目标消息率和目标报文大小，观察 Spring 堆内存、CPU、GC 和落后时间。
4. 按单节点实测容量配置流媒体分片数，并保留 30% 以上余量。
5. 做 Broker、流媒体、后端、Nginx 各一次故障切换，确认客户端能自动恢复。

单机只适合功能验证和小规模试运行。万级项目必须经过上述压测后再确定节点数量和存储规模。
